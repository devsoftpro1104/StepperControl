# Independent Watchdog (IWDG)

Источник правды: [firmware/src/app/src/tasks/task_watchdog.c](../firmware/src/app/src/tasks/task_watchdog.c). Документ описывает поведение **после** старта планировщика FreeRTOS.

## Зачем нужен

Аппаратный страховой механизм: если RTOS зависнет (дедлок, стек-оверфлоу, бесконечный цикл в высокоприоритетной задаче) и `wdg`-задача не получит CPU дольше таймаута — IWDG безусловно ресетнёт МК. В отличие от software-watchdog внутри FreeRTOS, IWDG тактируется собственным независимым LSI-генератором и переживёт даже отказ HSE/PLL.

## Параметры

| Параметр                   | Значение            | Откуда                               |
|----------------------------|---------------------|--------------------------------------|
| Источник тактирования      | LSI ≈ 32 кГц        | RM0090 §22.3, `LL_IWDG_Enable` стартует LSI автоматически |
| Prescaler                  | `LL_IWDG_PRESCALER_32` | `task_watchdog.c` — `watchdog_init()` |
| Тик IWDG                   | 1 мс                | `LSI / 32 ≈ 32000 / 32 = 1000 Гц`     |
| Reload value               | 1000                | `WATCHDOG_TIMEOUT_TICKS` в `task_watchdog.c` |
| Таймаут                    | ~1 с                | `1000 × 1 мс`                         |
| Период reload в задаче     | 200 мс              | `WATCHDOG_RELOAD_PERIOD_MS`           |
| Запас                      | ×5                  | `1000 / 200`                          |

LSI на STM32F407 имеет разброс **17–47 кГц** по даташиту (typ. 32). При худшем случае (47 кГц) реальный таймаут составит `1000 × (32/47) ≈ 680 мс`, при лучшем (17 кГц) — `1000 × (32/17) ≈ 1.88 с`. Запас в 5× выбран так, чтобы даже при минимальном фактическом таймауте оставался комфортный буфер на jitter планировщика.

## Последовательность инициализации

Один раз в начале `task_watchdog`, до основного цикла:

```
1. LL_IWDG_Enable(IWDG)              ; 0xCCCC → KR — старт IWDG, авто-старт LSI
2. LL_IWDG_EnableWriteAccess(IWDG)   ; 0x5555 → KR — снимает защиту PR/RLR
3. LL_IWDG_SetPrescaler(LL_IWDG_PRESCALER_32)
4. LL_IWDG_SetReloadCounter(1000)
5. while (LL_IWDG_IsReady(IWDG) == 0) ; ждём очистки PVU/RVU в SR
6. LL_IWDG_ReloadCounter(IWDG)       ; 0xAAAA → KR — обновляет счётчик и закрывает write access
```

После шага 1 IWDG уже считает с дефолтными параметрами (PR=0, RLR=0xFFF → ~512 мс). Шаги 3–4 настраивают целевые значения; шаг 5 ждёт, пока теневые регистры не синхронизируются с активными (иначе ранний reload в шаге 6 может промахнуться).

## Основной цикл

```c
for (;;) {
    LL_IWDG_ReloadCounter(IWDG);   // 0xAAAA → KR
    osDelay(WATCHDOG_RELOAD_PERIOD_MS);
}
```

Обоснование, почему 200 мс достаточно:

- Приоритет `wdg` — `Normal`. Выше — только `motor` (`AboveNormal`). Если `motor` залипнет в исполнении notification-handler'а на >1 с, это уже само по себе аномалия, заслуживающая ресета.
- Все «долгие» вызовы (DS18B20 conversion ~760 мс, `vsnprintf`, ADC-проходы probe ~5 мс) живут в **других** задачах. `wdg` не делает ничего блокирующего, кроме `osDelay`.
- Стек 256 байт — никаких локальных аллокаций, ни `printf`, ни глубоких цепочек вызовов.

## Подводные камни

- **IWDG нельзя остановить.** После `LL_IWDG_Enable` единственный способ выключить — аппаратный reset. Это by design; не пытаться «временно глушить» через регистры.
- **LSI продолжает считать в Sleep/Stop/Halt.** При отладке через ST-Link/J-Link «пауза» в IDE не останавливает IWDG, и через ~1 с после первого `wdg`-reload отладочная сессия будет прервана ресетом. Если нужна нормальная пошаговая отладка — заморозить IWDG в DEBUG-моде:
  ```c
  __HAL_DBGMCU_FREEZE_IWDG();           // или эквивалент:
  DBGMCU->APB1FZ |= DBGMCU_APB1_FZ_DBG_IWDG_STOP;
  ```
  В проекте сейчас это **не настроено** — добавить только при необходимости debug-сборки.
- **Разброс LSI.** См. таблицу выше — реальный таймаут может отличаться от номинального почти втрое. Поэтому `WATCHDOG_TIMEOUT_TICKS` нельзя ужимать ради «точности» — запас по reload-периоду должен покрывать худший случай.
- **Reload value ограничен 12 битами.** `RLR[11:0]`, максимум `4095`. С `prescaler /256` — потолок таймаута ~33 с. Этого хватает; если внезапно понадобится больше — потребуется внешняя hardware-схема, IWDG не масштабируется.
- **`LL_IWDG_IsReady` после `Enable`.** Если пропустить шаг 5 и сразу делать reload — может сработать с ещё «старыми» теневыми регистрами. Симптом — кажется, что таймаут короче, чем считали. Лечится корректной последовательностью init.
- **Только одна задача-кормилец.** Поскольку reload может быть из любой точки кода, легко устроить «бесконечно живой watchdog» через bug — например, кормить из ISR таймера, который никогда не останавливается. Архитектурное правило: reload **только** из `task_watchdog`, чтобы зависание планировщика гарантированно приводило к ресету.

## Где менять

- Параметры (prescaler, reload, период reload) — только [task_watchdog.c](../firmware/src/app/src/tasks/task_watchdog.c).
- Подключение модуля LL (`LL_IWDG_MODULE_ENABLED` + include) — [stm32f4xx_ll_conf.h](../firmware/src/config/stm32f4xx_ll_conf.h).
- DEBUG-freeze (если потребуется) — добавить рядом с `bsp_clock_init_*` в [bsp_clock.c](../firmware/src/bsp/src/bsp_clock.c) под условием `#ifdef DEBUG`.
