# AH49E — линейный Hall-датчик

Сводка по прошивочной интеграции AH49E: что подключено, как опрашивается,
какие команды CLI, какие коды ошибок и в каком потоке всё выполняется.
Архитектура в точности повторяет [DS18B20](ds18b20.md): `driver → device →
service → task`, но с одним важным отличием — здесь чтение **не блокирующее**,
АЦП крутится в DMA-circular непрерывно.

## Что это за датчик

AH49E (Diodes Inc / OEM-клоны под номером «49E») — **аналоговый линейный
датчик Холла**. Выход — напряжение, пропорциональное магнитной индукции:

| Параметр                | Типовое значение                  |
|-------------------------|-----------------------------------|
| Питание (Vcc)           | 2.7 … 6.5 В                        |
| Ток покоя               | ≈ 5 мА                             |
| Выход                   | **аналоговый**, линейный           |
| Чувствительность        | ≈ 1.4 мВ/Гс @ 5 В, ≈ 0.92 мВ/Гс @ 3.3 В |
| Уровень при B = 0       | ≈ Vcc / 2                          |
| Полярность              | биполярный — N выше середины, S ниже |
| Корпус                  | TO-92S, 3 пина: VCC, OUT, GND      |

«Линейный» здесь означает: AH49E **не** триггер Шмитта, в отличие от A3144 /
US5881. Это важно — для считывания нужен АЦП, а не GPIO.

## Аппаратное подключение

| Сигнал   | Пин на MCU | Режим                                 |
|----------|------------|---------------------------------------|
| OUT      | **PA1**    | analog input → **ADC1_IN1**           |
| VCC      | 3.3 В      | от платы STM32 (или 5 В при наличии делителя) |
| GND      | GND        |                                       |

Источник правды по выводу — [`PIN_HALL_*`](../firmware/src/bsp/inc/bsp_pins.h)
в `bsp_pins.h`. На STM32F4 PA1 — это **ADC1/2/3 канал 1**, любой из трёх ADC
теоретически может его читать; драйвер использует ADC1.

> **Внимание (Discovery):** на этой плате VREF+ через перемычку SB12 заведён
> на 3.3 В. Если используешь кастомную плату — измерь VDDA и при необходимости
> поправь `VREF_MV` в [`ah49e.c`](../firmware/src/devices/ah49e/src/ah49e.c#L7).
>
> **Питание AH49E:** при питании от 5 В выход датчика будет в районе 2.5 В,
> что **превышает 3.3 В при больших полях** в направлении одного из полюсов.
> На вход АЦП можно подавать максимум VDDA ≈ 3.3 В, иначе клампинговые диоды
> просядут питание и измерение «сядет на потолок». Решения: **либо питать
> AH49E от 3.3 В** (теряем половину чувствительности — 0.92 мВ/Гс),
> **либо ставить резистивный делитель 1:2** между OUT и PA1.

## АЦП — конфигурация

Драйвер: [`firmware/src/drivers/adc/`](../firmware/src/drivers/adc/).

| Параметр                 | Значение                           | Почему                          |
|--------------------------|------------------------------------|---------------------------------|
| Ядро                     | **ADC1**                           | Канал 1 → PA1                   |
| Разрядность              | 12 бит (0..4095)                   | Больше всё равно избыточно для 1.4 мВ/Гс |
| Тактирование             | PCLK2 / 4 = **21 МГц**             | Макс 36 МГц по datasheet, /4 — самый стабильный |
| Sample time              | **480 циклов** (≈ 23 мкс / sample) | Низкоомный выход AH49E ≤ ~1 кΩ — но избыток помехоустойчивости бесплатен |
| Режим                    | Continuous + DMA-circular          | Один канал крутится сам, CPU не дергается |
| Выравнивание             | Right                              | Стандарт                        |
| Триггер                  | Software (один раз на старте)      | Continuous подхватывает         |

## DMA — конфигурация

| Параметр              | Значение                          |
|-----------------------|-----------------------------------|
| Контроллер            | **DMA2**, Stream 0, Channel 0     |
| Направление           | PERIPH → MEMORY                   |
| Источник              | `&ADC1->DR`                       |
| Приёмник              | `s_adc_buf[16]` (статика, .bss)   |
| Размер слова          | half-word (16 бит)                |
| Mode                  | **Circular**                      |
| FIFO                  | DISABLE (direct mode)             |
| Приоритет             | LOW (UART_TX выше)                |
| Прерывания            | **не используются**               |

**Почему DMA, а не software-конвертация?** При software MCU ждал бы EOC
~23 мкс на каждый сэмпл и за это время мог бы делать что-то полезное.
DMA в circular освобождает ядро полностью: ring sample-buffer всегда
содержит свежие 16 значений, чтение из API — это просто `memcpy` нескольких
half-word'ов и среднее. Ни блокировок, ни прерываний.

**Распределение DMA контроллеров в проекте:**

| DMA / Stream / Channel  | Использование                  |
|-------------------------|--------------------------------|
| DMA1 Stream 6 Ch 4      | USART2_TX                      |
| **DMA2 Stream 0 Ch 0**  | **ADC1 → ring sample-buffer**  |

ADC может работать только с DMA2 (RM0090 §10.3.1). Stream 4 Ch 0 — резерв
под второй канал ADC1, если когда-нибудь потребуется.

## Архитектура (по слоям)

```
   PA1 (analog)
      │
      ▼
  ┌──────────────────────────────────────────────────┐
  │ ADC1 + DMA2 Stream 0  (continuous, circular)     │   ← driver
  │   sample_buf[16] ←  ADC->DR  каждые 23 мкс       │
  └──────────────────────────────────────────────────┘
      │ adc_hall_raw_avg() / adc_hall_raw_latest()
      ▼
  ┌──────────────────────────────────────────────────┐
  │ ah49e:  raw → mV, raw → centered, zero calib     │   ← device
  └──────────────────────────────────────────────────┘
      │ ah49e_read_raw / read_mv / read_centered
      ▼
  ┌──────────────────────────────────────────────────┐
  │ task_hall:                                       │   ← task
  │   if (running) → read + publish + UART $H        │
  │   else         → osDelay(IDLE_POLL_MS)           │
  └──────────────────────────────────────────────────┘
      │       │
      │       └─► uart2_send("$H, ts, raw, c\r\n")
      ▼
  ┌──────────────────────────────────────────────────┐
  │ hall_service: last raw + centered + ts (volatile)│   ← service
  └──────────────────────────────────────────────────┘
      ▲
      │ hall_service_get_last()
      │
   shell.c (HALL READ)        task_telemetry (резерв)
```

## FreeRTOS-задача `task_hall` (детально)

Файл: [`firmware/src/app/src/tasks/task_hall.c`](../firmware/src/app/src/tasks/task_hall.c).
Создание — в [`app_main.c::app_run()`](../firmware/src/app/src/app_main.c).

```c
extern void task_hall(void *argument);
...
osThreadAttr_t a = s_attr_default;
a.name       = "hall";
a.stack_size = 1024;          /* snprintf + локальные буферы */
a.priority   = osPriorityNormal;
osThreadNew(task_hall, NULL, &a);
```

### Параметры потока

| Параметр       | Значение            | Почему именно так |
|----------------|---------------------|-------------------|
| Имя            | `"hall"`            | Видно в `vTaskList()` рядом с `temp`, `diag` |
| Стек           | **1024 байт**       | snprintf newlib-nano + buf[48] = пик ~600 байт; запас на ISR |
| Приоритет      | `osPriorityNormal`  | Совпадает с `temp`/`telem`/`protocol`/`diag` |
| Аргумент       | `NULL`              | Состояние шарится через `hall_service` |
| Тип            | Динамический        | Все потоки в проекте через `osThreadNew` |

### Жизненный цикл

```
   bsp_init()  →  ah49e_init()  →  adc_init()
        │             │
        │             └─► ADC1 непрерывно крутится с этого момента,
        │                  ring-buffer заполняется через DMA
        ▼
   osKernelInitialize()
        │
        ▼
   osThreadNew(task_hall, …)
        │
        ▼
   osKernelStart()
        │
        ▼
   ┌──────────────────────────────────────────────────┐
   │  task_hall main loop:                            │
   │                                                  │
   │  if (!hall_service_running())                    │
   │      osDelay(IDLE_POLL_MS=200)   ── BLOCKED      │
   │  else                                            │
   │      raw = ah49e_read_raw()         (~ns!)       │
   │      c   = ah49e_read_centered()    (~ns!)       │
   │      hall_service_publish(raw, c)                │
   │      uart2_send("$H, ts, raw, c\r\n")            │
   │      osDelay(period_ms)             ── BLOCKED   │
   │                                                  │
   └──────────────────────────────────────────────────┘
```

В отличие от `task_temp` здесь **нет блокирующего чтения** — `ah49e_read_*`
это просто доступ к памяти (среднее по 16 sample'ам ring-buffer'а). Период
определяется только желаемой частотой публикации в UART, не временем
конвертации.

### Состояния

| Состояние FreeRTOS | Когда                                              | Длительность |
|--------------------|----------------------------------------------------|--------------|
| `BLOCKED` (delay)  | `hall_service_running()==false`                    | 200 мс       |
| `BLOCKED` (delay)  | `osDelay(period_ms)` между публикациями            | 10 … 60000 мс|
| `RUNNING`          | snprintf + uart2_send + чтение ring-buffer'а       | < 1 мс       |
| `READY`            | Между Wake-up и реальным запуском                  | — |

### Почему `IDLE_POLL_MS = 200`

То же обоснование, что и в `task_temp`: компромисс между лагом на
`HALL START` и сложностью. Если потребуется реакция за миллисекунды —
заменить на `osEventFlagsWait(... osWaitForever)` + флаг из
`hall_service_start()`/`hall_service_set_period_ms()`.

### Взаимодействие с другими задачами

```
   shell  ──► HALL READ  ──► ah49e_read_*()  ─┐
                                              │  обращение
   task_hall ──► ah49e_read_*()  ─────────────┤  к одному
                                              │  ring-buffer'у
   task_telemetry (резерв) ──► hall_service_get_last()
                                              ▼
                                  ┌─────────────────────┐
                                  │ s_adc_buf[16]       │ ← DMA пишет сюда
                                  │ (volatile uint16)   │
                                  └─────────────────────┘
```

- **Гонок за шину нет**: ADC + DMA — single-writer, читать ring можно из
  любой задачи без мьютекса; volatile + atomic-доступ к 16-bit на M4
  достаточны.
- **Соседи через `hall_service`**: `task_telemetry` может в перспективе
  подмешивать поле в свой `$T` — пока этого не делает (там только
  температура). Если понадобится — добавить колонку `<hall>` в формат
  и `hall_service_get_last(...)` в task_telemetry.

### Анализ стека

| Кадр                               | Прибл. размер   |
|------------------------------------|-----------------|
| TCB save area / RTOS overhead      | ~80 байт        |
| `task_hall` локальные              | ~60 байт (`buf[48]`, `raw`, `c`, `n`) |
| `vsnprintf` newlib-nano            | ~300–400 байт   |
| `uart2_send` + LL                  | ~30 байт        |
| Запас на ISR-кадр                  | ~100 байт       |
| **Итого пик**                      | **≈ 550–650 байт** |

1024 — комфортный запас.

## API устройства AH49E

[`firmware/src/devices/ah49e/inc/ah49e.h`](../firmware/src/devices/ah49e/inc/ah49e.h):

| Функция                       | Возвращает / делает                                       |
|-------------------------------|-----------------------------------------------------------|
| `ah49e_init()`                | Поднимает ADC + DMA. Вызывается из `bsp_init()` ДО `osKernelStart()`. |
| `ah49e_read_raw()`            | uint16_t 0..4095 — среднее 16 сэмплов из ring             |
| `ah49e_read_mv()`             | uint16_t — миллиВольты при VREF=3.3 В                     |
| `ah49e_read_centered()`       | int16_t — `raw - zero_offset`. Если калибровка не сделана — `raw - 2048`. |
| `ah49e_calibrate_zero()`      | Записывает текущий raw как ноль; возвращает зафиксированный offset |
| `ah49e_clear_zero()`          | Сбрасывает калибровку                                     |
| `ah49e_zero_is_set()`         | true если `ah49e_calibrate_zero()` был вызван             |
| `ah49e_zero_get()`            | Текущий offset (либо 2048 если калибровка не сделана)     |

## CLI команды (USART2, shell)

Реализация — [`shell.c::cmd_hall`](../firmware/src/middleware/shell/src/shell.c).

| Команда             | Действие                                            | Ответ |
|---------------------|-----------------------------------------------------|-------|
| `HALL READ`         | Разовое чтение, без блокировок (~миллисек)          | `+OK HALL raw=<n> mv=<n> centered=<±n>` |
| `HALL ON`           | Включить поток `$H,<ts>,<raw>,<centered>`           | `+OK HALL ON` |
| `HALL OFF`          | Выключить поток                                     | `+OK HALL OFF` |
| `HALL RATE <hz>`    | Частота публикации (1..100 Hz)                      | `+OK HALL RATE <hz>` / `-ERR HALL bad-rate min=1 max=100` |
| `HALL ZERO`         | Записать текущее значение как «ноль» (B = 0)        | `+OK HALL ZERO offset=<raw>` |
| `HALL ZEROCLR`      | Сбросить калибровку                                 | `+OK HALL ZEROCLR` |

Частота по умолчанию — **10 Гц** (period 100 мс). Максимум **100 Гц** —
быстрее бессмысленно: один кадр `$H` ≈ 25 байт на 115200 = ~2.2 мс на UART,
а пользовательское восприятие потока всё равно ничего сверху не различает.

## Стримы телеметрии

| Стрим                                         | Источник         | Когда отправляется |
|-----------------------------------------------|------------------|--------------------|
| `$H, <ts_ms>, <raw>, <centered>\r\n`          | `task_hall`      | Каждый период, если `HALL START` |

Поля:
- `<raw>` — 0..4095, усреднённое 16-сэмплами
- `<centered>` — signed, `<raw> - <zero_offset>`. Если HALL ZERO не
  выполнялся — относительно теоретического mid (2048).

## Калибровка нуля — зачем

AH49E на холостом ходу выдаёт **не ровно** Vcc/2, а с разбросом по
datasheet ±150 мВ. Кроме того, на pcb-level есть собственное магнитное
смещение (близкие дорожки питания, феромагнитные элементы корпуса).
Поэтому до начала измерений нужно:

1. Удалить магнит / поставить датчик в положение «нет внешнего поля».
2. Подождать 1-2 секунды, чтобы ring sample-buffer заполнился свежими
   сэмплами без переходного процесса.
3. Послать `HALL ZERO`. Прошивка зафиксирует текущий усреднённый raw
   как новый «ноль».
4. С этого момента `<centered>` в стриме `$H` будет давать **знак и
   величину отклонения** от калиброванного нуля.

Калибровка хранится **только в RAM** — после reset придётся повторить.
В перспективе — сохранять в EEPROM (когда подключим I2C1 на PB6/7).

## Перевод counts → физика

При питании AH49E от **3.3 В** и VREF АЦП = 3.3 В:

```
один count  =  3300 мВ / 4095        ≈  0.806 мВ
один Гс     ≈  0.92 мВ               ≈  1.14 count
```

То есть `centered` напрямую читается как **примерно «counts ≈ Гсс ÷ 0.88»**
или **«mGs ≈ centered × 880»**. Точный коэффициент зависит от Vcc и
индивидуального экземпляра — для метрологии нужна ваша калибровка с
эталонным магнитом, для индикации/триггеров достаточно.

При питании от **5 В** через резистивный делитель 1:2 — амплитуда сигнала
делится пополам, значит и итоговая чувствительность × 0.5: `mGs ≈ centered × 1760`.

## Известные ограничения

- **Один канал**, один пользователь (AH49E на PA1). Если потребуется
  второй ADC-канал (например, для тока мотора) — драйвер `adc.c` нужно
  переписать на scan-mode + ranks, а ring-buffer станет
  `[NUM_CHANNELS][BUF_LEN]` или с offsetом по индексу.
- **Калибровка нуля живёт в RAM** — теряется после reset.
- **Нет защиты от обрыва**: если PA1 «болтается» (датчик отключён),
  АЦП будет читать дрейфующий шум от антенны. Драйвер не отличает это
  от нормального сигнала на холостом ходу. Для детекта обрыва можно
  включить внутренний weak pull-down на PA1 — но это испортит
  измерение, поэтому намеренно не сделано.
- **Единое VREF=3300 мВ зашито в коде**. На кастомных платах с другим
  VDDA — поправить вручную в `ah49e.c`.
