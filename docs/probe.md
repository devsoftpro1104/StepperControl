# PROBE — самодиагностика STEP-сигнала

ADC2-самописец на пине PA0, подключённом перемычкой к PA8 (STEP). Позволяет
не выходя из платы убедиться, что таймер TIM1 действительно генерирует
импульсы заданной частоты с ровными CMOS-уровнями. Стрим публикует две
величины: оценку частоты `freq_hz` и DC-компоненту `adc` (для PWM 50 %
ожидаем `adc ≈ 2048`). Сырая waveform доступна через `PROBE DUMP`.

Архитектура — точно та же, что у AH49E: `driver → service → task → CLI`.
Используется отдельный ADC2 (не мешает AH49E на ADC1).

## Аппаратное подключение

Единственное требование — перемычка между двумя пинами одной и той же
платы:

```
   PA8 ●────────[wire]────────● PA0
   STEP                         ADC2_IN0
   (TIM1_CH1 PWM out)           (analog in)
```

Без перемычки `PROBE` будет читать болтающийся вход и показывать шум
антенны (десятки–сотни counts вокруг ~2000).

## АЦП — конфигурация

Драйвер: [`firmware/src/drivers/adc_probe/`](../firmware/src/drivers/adc_probe/).

| Параметр                 | Значение                            | Почему                          |
|--------------------------|-------------------------------------|---------------------------------|
| Ядро                     | **ADC2**                            | ADC1 уже занят AH49E            |
| Канал                    | 0 (PA0)                             | ADC2_IN0                        |
| Разрядность              | 12 бит (0..4095)                    | Стандарт                        |
| Тактирование             | PCLK2 / 4 = **21 МГц** (общий с ADC1) | `LL_ADC_SetCommonClock` idempotent |
| Sample time              | **28 циклов** (≈1.9 µs / sample)    | Бинарный сигнал — шум не важен; нужен высокий sample rate |
| Sample rate              | **525 kSPS**                        | (28+12)/21 МГц                   |
| Режим                    | Continuous + DMA-circular           | Один канал крутится сам         |
| Триггер                  | Software (один раз на старте)       | Continuous подхватывает         |

## DMA — конфигурация

| Параметр              | Значение                          |
|-----------------------|-----------------------------------|
| Контроллер            | **DMA2**, Stream **2**, Channel 1 |
| Направление           | PERIPH → MEMORY                   |
| Источник              | `&ADC2->DR`                       |
| Приёмник              | `s_buf[4096]` (.bss, **8 КБ**)    |
| Размер слова          | half-word (16 бит)                |
| Mode                  | Circular                          |
| FIFO                  | DISABLE                           |
| Приоритет             | LOW                               |
| Прерывания            | не используются                   |

**Окно времени:** `4096 / 525000 ≈ 7.8 мс`. Это значит:
- Дискретизация `freq_hz` — `SAMPLE_HZ / (2 × BUF_LEN) ≈ **64 Hz**`. Возможные
  значения: 0, 64, 128, 192, … Минимум для уверенно измеряемого периодического
  сигнала — **128 Hz** (одна пара переходов = одна полная волна в окне);
  ниже — `freq_hz` округляется к 0 (хотя `adc` ещё показывает DC-уровень).
- На частоте **2 кГц** в окне умещается ~15 периодов — отличная
  статистика.
- На частоте **200 кГц** в окне ~1560 периодов, но всего ~2.6 семпла на
  период — оценка `freq_hz` остаётся точной, а форма импульса в `PROBE DUMP`
  будет выглядеть «зубчато» из-за алиасинга.

**Распределение DMA-контроллеров в проекте:**

| DMA / Stream / Channel  | Использование                  |
|-------------------------|--------------------------------|
| DMA1 Stream 6 Ch 4      | USART2_TX                      |
| DMA2 Stream 0 Ch 0      | ADC1 → AH49E ring              |
| **DMA2 Stream 2 Ch 1**  | **ADC2 → STEP probe ring**     |

## Алгоритм статистики

Один проход по ring-буферу (4096 сэмплов) на каждом тике задачи. Порог
логического «1» — 2048 (середина диапазона АЦП).

```
sum               ← сумма всех сэмплов
transitions       ← число переходов через порог 2048
adc               ← sum / 4096                    (среднее, 0..4095)
freq_hz           ← transitions * SAMPLE_HZ / (2 * BUF_LEN)
```

`adc` — это DC-компонента сигнала. Для PWM 50% даст ~2048; для PWM 25%
даст ~1024; для постоянного 3.3 В — ~4095; для GND — ~0. По сути
эквивалент тяжёлого low-pass фильтра без отдельного DSP.

Без гистерезиса: при чистых фронтах STEP (≤ 100 нс на CMOS-выходе)
вероятность поймать сэмпл точно посреди фронта — ~1 / 4096, статистике
не мешает.

CPU-стоимость: ~5 мс на проход (4096 итераций с min/max/счётчиками на
M4 168 МГц). На дефолтных 2 Hz — 1% CPU. На макс 50 Hz — 25%.

## Архитектура (по слоям)

```
   PA8 (STEP, TIM1_CH1)
      │
      │  перемычка
      ▼
   PA0 (analog)
      │
      ▼
  ┌──────────────────────────────────────────────────┐
  │ ADC2 + DMA2 Stream 2 (continuous, circular)      │  ← driver
  │   sample_buf[4096] ←  ADC2->DR  каждые 1.9 µs    │
  └──────────────────────────────────────────────────┘
      │ adc_probe_get_stats()
      ▼
  ┌──────────────────────────────────────────────────┐
  │ stats compute: freq_hz, adc (DC-уровень)         │  (driver-level)
  └──────────────────────────────────────────────────┘
      │
      ▼
  ┌──────────────────────────────────────────────────┐
  │ task_probe:                                      │  ← task
  │   if (running) → compute + publish + UART $P     │
  │   else         → osDelay(IDLE_POLL_MS)           │
  └──────────────────────────────────────────────────┘
      │       │
      │       └─► uart2_send("$P, ts, freq_hz, adc\r\n")
      ▼
  ┌──────────────────────────────────────────────────┐
  │ probe_service: last stats + ts (volatile)        │  ← service
  └──────────────────────────────────────────────────┘
      ▲
      │ probe_service_get_last() / shell PROBE READ
```

## CLI

| Команда             | Действие                                            | Ответ |
|---------------------|-----------------------------------------------------|-------|
| `PROBE READ`        | Однократный анализ + ответ строкой                  | `+OK PROBE freq=<hz> adc=<n>` |
| `PROBE ON`          | Включить поток `$P,<ts>,<freq>,<adc>`               | `+OK PROBE ON` |
| `PROBE OFF`         | Выключить поток                                     | `+OK PROBE OFF` |
| `PROBE RATE <hz>`   | Частота публикации (1..50 Hz, дефолт 2)             | `+OK PROBE RATE <hz>` / `-ERR PROBE bad-rate min=1 max=50` |
| `PROBE DUMP`        | Снимок текущего ring'а (4096 сэмплов hex), для построения waveform на хосте | многострочный (см. ниже) |

## FreeRTOS-задача `task_probe`

| Параметр       | Значение            | Почему |
|----------------|---------------------|--------|
| Имя            | `"probe"`           | Видно в `vTaskList()` рядом с `hall`, `temp` |
| Стек           | 1024 байт           | snprintf + локальные ~600 Б пик |
| Приоритет      | `osPriorityNormal`  | Не критично по времени, обычная фоновая задача |
| Блокировка     | `osDelay(period)`   | Никаких ISR-уведомлений; всё самодостаточно крутится |

## PROBE DUMP — сырая waveform

Когда `$P`-стрим (одно усреднённое значение в окне) не позволяет увидеть
форму импульса, есть команда `PROBE DUMP`. Она снимает текущий ring-буфер
(4096 сэмплов, окно 7.8 мс при sample rate 525 kSPS) и отдаёт его одним
блоком в hex-CSV.

### Протокол

```
+OK PROBE DUMP begin samples=4096 sample_hz=525000
$D, 0,  <128 hex×3>
$D, 1,  <128 hex×3>
...
$D, 31, <128 hex×3>
+OK PROBE DUMP end
```

- 32 строки тела × 128 семплов = 4096.
- Каждый сэмпл = 3 hex-символа (12 бит, 0..0xFFF).
- Хронологический порядок: `chronological_idx 0` — самый старый сэмпл в
  окне, `4095` — самый свежий. На графике ось времени растёт вправо.
- На время дампа DMA приостановлен → `$P`-стрим, если `PROBE ON`,
  пропускает ~1.1 секунды и автоматически возобновляется после `end`.
- Объём: 32 × ~390 байт ≈ 12.5 КБ → ~1.1 секунды на 115200 baud.

### Связка с временем

Каждый сэмпл отдалён от соседа на `1 / sample_hz = 1.9 мкс`. Для оси
времени на графике:

```
t_us[i] = i * 1_000_000 / sample_hz
```

При sample_hz=525000 шаг ≈ **1.905 мкс**, всё окно ≈ 7.8 мс.

### Парсер на PySide6

```python
import re
from PySide6.QtSerialPort import QSerialPort

class ProbeDumpCollector:
    """Собирает один PROBE DUMP. Использование:
       1) port.write(b"PROBE DUMP\\r\\n")
       2) на каждый readyRead() передавать полученные строки в .feed()
       3) когда .complete=True — забрать .samples (np.ndarray) и .sample_hz."""

    _hdr = re.compile(r"^\+OK PROBE DUMP begin samples=(\d+) sample_hz=(\d+)$")
    _row = re.compile(r"^\$D,\s*(\d+),\s*([0-9a-fA-F]+)$")
    _end = "+OK PROBE DUMP end"

    def __init__(self):
        self.samples   = None
        self.sample_hz = None
        self.complete  = False

    def feed(self, line: str):
        line = line.rstrip("\r\n")
        if (m := self._hdr.match(line)):
            n            = int(m.group(1))
            self.sample_hz = int(m.group(2))
            self.samples = [0] * n
            self.complete = False
            return
        if line == self._end:
            self.complete = True
            return
        if (m := self._row.match(line)) and self.samples is not None:
            idx, hexdata = int(m.group(1)), m.group(2)
            line_samples = 128
            for i in range(line_samples):
                v = int(hexdata[i*3:(i+1)*3], 16)
                self.samples[idx * line_samples + i] = v
```

И построение графика поверх `pyqtgraph.PlotWidget` или `matplotlib`:

```python
import numpy as np
import pyqtgraph as pg

def plot_dump(collector):
    samples = np.array(collector.samples, dtype=np.uint16)
    t_us    = np.arange(len(samples)) * 1_000_000 / collector.sample_hz
    # на 3.3 В шкалу:
    v_volts = samples * 3.3 / 4095
    pw = pg.PlotWidget(title="PROBE DUMP")
    pw.plot(t_us, v_volts, pen='y')
    pw.setLabel('bottom', 'time, µs')
    pw.setLabel('left',   'voltage, V')
    pw.show()
```

### Что увидишь на графике

| Сценарий                                      | Картинка                              |
|-----------------------------------------------|---------------------------------------|
| Активный `MOVE 1000000 1000` (1 кГц)         | прямоугольный меандр, 7-8 периодов в окне, фронты на уровне ~3.3 В, плато ~0 В и ~3.3 В |
| Активный `MOVE 1000000 5000` (5 кГц)         | 39 периодов в окне, фронты по-прежнему резкие |
| Idle (нет `MOVE`)                             | Hi-Z болтанка ~1.5..2.5 В, без фронтов |
| Очень быстрый STEP (200 кГц)                  | 1560 периодов; форма видна как «зубчатый» паттерн с ~2.6 семплов на период |

На частоте 1 кГц сигнала и `sample_hz` 525 kSPS получится **~525 точек на
период PWM** — отлично виден фронт, плато, спад. Можно оценить:
- Время нарастания фронта (если МК и/или нагрузка медленные)
- Просадки/звон на плато
- Несимметричность duty в реальности vs. CCR=ARR/2

### Подводные камни DUMP

1. **Снимок «во времени точечный».** За 1.1 секунды передачи мотор
   успевает «уехать», но в самом ring'е сохранены семплы за 7.8 мс на
   момент `begin`. Передача — это просто чтение замороженной памяти.
2. **Между двумя DUMP'ами без `MOVE` ring остаётся в одном состоянии**
   потому что ADC хоть и продолжает конвертировать, в DR копится один
   и тот же мусор от Hi-Z.
3. **Не запускать DUMP во время длинной публикации `$P RATE 50`** —
   на хосте получится перемешанный поток `$P` и `$D`. Парсер выше
   корректно ловит `$D` по префиксу, но удобнее `PROBE OFF` перед DUMP.

## Сценарии использования

### 1. Быстрая проверка PWM на старте

```
MOVE 1000000 1000         ← длинный пакет на 1 кГц (~16 минут)
PROBE READ                ← во время движения
   +OK PROBE freq=1000 adc=2050
```

`freq` совпадает со speed_sps; `adc≈2048` означает DC ≈ Vcc/2 →
PWM 50 % duty (CCR=ARR/2 в TIM1).

### 2. Непрерывный мониторинг

```
PROBE ON
MOVE 100000 5000
   $P, 12345, 5000, 2049
   $P, 12845, 5000, 2050
   $P, 13345, 5000, 2048
   ...
   !DONE MOVE
   $P, 33345, 128,  2380       ← STEP остановлен → MOE=0 → PA8 в Hi-Z;
                                  ADC показывает шум вокруг середины
PROBE OFF
```

### 3. «Idle-чтение» — что значат странные числа

После `step_pwm_init()` и между движениями PA8 в **Hi-Z** (TIM1.MOE=0
по умолчанию, off-state раскручен в «отключено»). Перемычка к PA0 →
аналоговый вход тоже high-Z с двух сторон → ADC показывает «болтающийся
вход»:

```
PROBE READ                  ← ничего сейчас не идёт
   +OK PROBE freq=128 adc=2379    ← это норма, не сигнал
```

- `adc ≈ 2000..2500` — наводка + leakage в районе VDDA/2.
- `freq` — либо 0, либо 128 (минимум различимого: 1 пара переходов через
  порог за 7.8 мс окна), либо 256 — это просто шум, пересекающий 2048.

Чтобы убедиться, что прошивка работает корректно, нужен **активный MOVE
во время чтения**.

### 3. Калибровка скорости

После реализации профиля — сверять заданную speed_sps с реально измеренной
freq в `$P`. Расхождение > 1 % указывает на ошибку в pre-scaler-арифметике
или дрейф HSE.

## Подводные камни

1. **STEP-выходы Hi-Z до первого MOVE.** В этом состоянии PA0 «болтается»,
   `adc` уплывает в район ~1500..2500 (наводка + leakage), `freq_hz` берёт
   рандомные значения 0/64/128/256 от случайных пересечений порога. Запускай
   `PROBE` после хотя бы одного `EN ON` (или сразу после `MOVE`).
2. **Короткие движения** (<100 шагов на 1 кГц = <100 мс) могут не попасть
   в окно публикации. Используй `PROBE READ` сразу после `MOVE` — он берёт
   текущий ring и сразу возвращает.
3. **Высокие STEP-частоты.** На 100+ кГц в окно влезает много периодов, но
   семплы редко попадают на «high»-участки. На `adc` это даёт небольшое
   смещение от теоретического 2048 при 50 % duty — это нормально, не баг.
4. **CPU-нагрузка при `PROBE RATE 50`.** ~25 % CPU на постоянный pass
   по 4096 значениям. Для отладки нормально, в продакшне держать ниже
   10 Hz.
5. **Конфликт пинов.** PA0 в этом проекте использован **только** под
   probe. Если когда-то понадобится что-то другое на PA0 — снять
   перемычку и переключить пин в нужный режим.
6. **Восстановление после `PROBE DUMP`.** Реализация в
   [adc_probe.c](../firmware/src/drivers/adc_probe/src/adc_probe.c)
   `adc_probe_dump_end()` чистит флаг OVR, заново включает DMA и перезапускает
   SW-trigger. Если этот шаг пропустить — после первого DUMP'а ADC2 поднимет
   OVR, остановит регулярный секвенсор, и `$P`/`READ` будут возвращать
   замёрзшие данные. Не правь `dump_end()` без понимания RM0090 §13.8.1.
