# DS18B20 — датчик температуры

Сводка по прошивочной интеграции DS18B20: что подключено, как опрашивается,
какие команды CLI, какие коды ошибок и в каком потоке всё выполняется.

## Аппаратное подключение

| Сигнал   | Пин        | Режим                         |
|----------|------------|-------------------------------|
| DQ       | **PB12**   | GPIO output, **open-drain**, speed HIGH, internal pull-up как страховка |
| VDD      | 3.3 В      | внешний резистор **4.7 кΩ от DQ к 3.3 В обязателен** |
| GND      | GND        |                               |

Первоисточник по выводу — [`PIN_DS18B20_*`](../firmware/src/bsp/inc/bsp_pins.h#L26-L27)
в `bsp_pins.h`. Внутренний WPU не вытягивает шину достаточно быстро на
длинных проводах, поэтому внешний 4.7к — обязательный, не «желательный».

## Шина и тайминги

Используется **1-Wire master, программный bit-bang на GPIO** (Maxim AN-126,
Standard speed). Микросекундные задержки реализованы через `DWT->CYCCNT`
(счётчик тактов ядра), `s_cyc_per_us = SystemCoreClock / 1 000 000`.
Драйвер: [`firmware/src/drivers/onewire/`](../firmware/src/drivers/onewire/).

| Слот / операция            | Код       | Длительность |
|----------------------------|-----------|--------------|
| reset low                  | `OW_T_H`  | 480 мкс      |
| reset wait → presence sample | `OW_T_I` | 70 мкс      |
| reset recovery             | `OW_T_J`  | 410 мкс      |
| write-1 low / read init    | `OW_T_A`  | 6 мкс        |
| write-1 tail               | `OW_T_B`  | 64 мкс       |
| write-0 low                | `OW_T_C`  | 60 мкс       |
| write-0 recovery           | `OW_T_D`  | 10 мкс       |
| read sample delay          | `OW_T_E`  | 9 мкс        |
| read tail                  | `OW_T_F`  | 55 мкс       |

Бит-слот ≈ 70 мкс, байт ≈ 0.6 мс, reset ≈ 1 мс. **Все транзакции выполняются
с глобально замаскированными прерываниями** (`__disable_irq()` на время
слота), иначе ISR съедет тайминг и устройство не увидит правильный slot.
Это потолок latency других ISR на время операции — стоит держать в уме.

## АЦП и DMA — почему их нет (для DS18B20)

DS18B20 сам по себе **не использует АЦП и не использует DMA**. Это цифровой
датчик с интерфейсом 1-Wire поверх одного GPIO; вся «оцифровка» происходит
внутри самого чипа, MCU только обменивается байтами по протоколу. DMA для
GPIO-bit-bang со строгими микросекундными слотами не применим в принципе —
управление линиями идёт инструкциями ядра под `__disable_irq()`.

В других модулях проекта АЦП и DMA, конечно, есть — это чисто заметка про
конкретно температурный путь:
- ADC1 + DMA2 Stream 0 — Hall AH49E на PA1 (см. [ah49e.md](ah49e.md)).
- ADC2 + DMA2 Stream 2 — STEP probe на PA0 (см. [probe.md](probe.md)).
- DMA1 Stream 6 — USART2 TX (shell + телеметрия).

## Размещение по задачам FreeRTOS

Создание потоков — в [`app_main.c`](../firmware/src/app/src/app_main.c).

| Задача         | Стек | Приоритет          | Что делает с DS18B20 |
|----------------|------|--------------------|----------------------|
| `temp`         | 1024 | `osPriorityNormal` | **Выделенный поток под датчик.** Периодический опрос (`Convert T → 760 мс → Read Scratchpad`), публикация в `temp_service` и эмиссия `$T18,...` в UART |
| `protocol`     | 2048 | `osPriorityNormal` | Через CLI выполняет синхронное `TEMP READ` (блокирует shell ≈770 мс) |
| остальные      | —    | —                  | `motor`, `hall`, `probe`, `diag`, `wdg` шину 1-Wire не трогают и DS18B20 не читают |

Шина — одна, доступ из `temp` и `protocol` сериализуется **мьютексом**
`s_bus_mutex` внутри `ds18b20_read_blocking()`
([`ds18b20.c:14`](../firmware/src/devices/ds18b20/src/ds18b20.c#L14)).
До старта планировщика мьютекс не работает — драйвер это явно проверяет
через `osKernelGetState()`.

## FreeRTOS-задача `task_temp` (детально)

Файл: [`firmware/src/app/src/tasks/task_temp.c`](../firmware/src/app/src/tasks/task_temp.c).
Создание — в [`app_main.c::app_run()`](../firmware/src/app/src/app_main.c) среди прочих
потоков:

```c
extern void task_temp(void *argument);   /* forward */
...
osThreadAttr_t a = s_attr_default;
a.name       = "temp";
a.stack_size = 1024;          /* snprintf + локальные буферы */
a.priority   = osPriorityNormal;
osThreadNew(task_temp, NULL, &a);
```

### Параметры потока

| Параметр       | Значение            | Почему именно так |
|----------------|---------------------|-------------------|
| Имя            | `"temp"`            | Видно в дампе FreeRTOS / `vTaskList()` |
| Стек           | **1024 байт**       | Локально: `char tstr[8]` + `char buf[48]` + аргументы snprintf. Newlib-nano `vsnprintf` без `%f` — самый прожорливый кадр в этой задаче. 256 не хватает — будет stack overflow в snprintf под нагрузкой. |
| Приоритет      | `osPriorityNormal`  | Совпадает с `protocol`/`hall`/`probe`/`diag`. Выше нельзя — задача 760 мс висит в `osDelay`, и если бы она вытесняла `motor` (`osPriorityAboveNormal`), это всё равно ничего не дало бы; ниже не нужно — задача добровольно отдаёт CPU через `osDelay`. |
| Аргумент       | `NULL`              | Состояние шарится через `temp_service` (volatile-поля), параметров на старте нет. |
| Тип            | Динамический (`osThreadNew`) | По проекту все потоки одинаково создаются через CMSIS-OS2 без `_Static_*`. |

### Жизненный цикл

```
   bsp_init()  →  ds18b20_init() (DWT + GPIOB12 OD, мьютекс шины)
        │
        ▼
   osKernelInitialize()
        │
        ▼
   osThreadNew(task_temp, …)        ← поток создан, но не выполняется
        │
        ▼
   osKernelStart()                  ← здесь начинается планирование
        │
        ▼
   ┌──────────────────────────────────────────────────┐
   │  task_temp main loop:                            │
   │                                                  │
   │  if (!temp_service_running())                    │
   │      osDelay(IDLE_POLL_MS=200)   ── BLOCKED      │
   │  else                                            │
   │      ds18b20_read_blocking()                     │
   │           ├─ osMutexAcquire     ── BLOCKED       │
   │           ├─ ow_reset / write   (с __disable_irq)│
   │           ├─ osDelay(760 мс)    ── BLOCKED       │
   │           ├─ ow_read scratchpad                  │
   │           └─ osMutexRelease                      │
   │      temp_service_publish + uart2_send($T18)     │
   │      osDelay(period - 760)      ── BLOCKED       │
   │                                                  │
   └──────────────────────────────────────────────────┘
```

Поток никогда не завершается: `task_temp` это бесконечный `for(;;)`. Удаление
не предусмотрено — если когда-нибудь понадобится «выключить датчик
полностью», достаточно `TEMP OFF`: задача уйдёт в `osDelay(IDLE_POLL_MS)`
и не будет дёргать шину.

### Состояния и где задача блокируется

| Состояние FreeRTOS | Когда                                                  | Длительность |
|--------------------|--------------------------------------------------------|--------------|
| `BLOCKED` (delay)  | `temp_service_running()==false` → `osDelay(IDLE_POLL_MS)` | 200 мс       |
| `BLOCKED` (mutex)  | Конкурент держит `s_bus_mutex` (CLI `TEMP READ` идёт параллельно) | до ≈770 мс — длительность чужого чтения |
| `BLOCKED` (delay)  | `osDelay(760)` пока DS18B20 конвертирует               | 760 мс       |
| `BLOCKED` (delay)  | `osDelay(period - 760)` между измерениями              | от 40 мс (period=800) до 59240 мс (period=60000) |
| `RUNNING`          | Только во время `ow_*` транзакций и `snprintf`         | суммарно несколько миллисекунд за цикл |
| `READY`            | Между Wake-up и реальным запуском, очень коротко       | — |

`task_temp` практически всё время в `BLOCKED` — это by design. CPU-budget
крошечный (~10 мс из 1 секунды при `period=1000`), большинство — это
ожидание DS18B20 либо ожидание следующего тика.

### Почему `IDLE_POLL_MS = 200`

Когда `TEMP OFF`, поток мог бы спать дольше (1–5 секунд) и так же быстро
просыпаться по флагу. Но мы сознательно держим **200 мс**:

- Реакция на `TEMP ON` через CLI должна быть «мгновенной» для
  пользователя — не больше пары тиков LED. 200 мс — это незаметный лаг.
- Можно было бы переделать на event-flag / semaphore, чтобы будить поток
  сразу при `temp_service_start()`. Но это +1 примитив и +код в shell;
  при текущей точности «опрос раз в секунду» это оверкилл.
- Если в будущем потребуется реакция за единицы миллисекунд — заменить на
  `osEventFlagsWait(... osWaitForever)` и сетить флаг из
  `temp_service_start()`/`temp_service_set_period_ms()`.

### Как взаимодействует с другими задачами

```
   protocol  ──► shell.c ──► ds18b20_read_blocking()  ─┐
                                                       │  s_bus_mutex
   temp      ──► ds18b20_read_blocking()  ─────────────┘  (osMutex)
                       │
                       ├──► temp_service_publish(c10)
                       │       │
                       │       ▼
                       │   ┌──────────────────┐
                       │   │ temp_service     │ (volatile поля)
                       │   └──────────────────┘
                       │       ▲
                       │       │ temp_service_get_last()
                       │       │
                       │   shell.c (TEMP READ ответ форматирует tstr из публикации)
                       │
                       └──► uart2_send($T18,...)
```

- **Конкурент `task_protocol`**: оба делают `ds18b20_read_blocking()`.
  Сериализация через `s_bus_mutex` гарантирует, что reset/Convert/Read
  не перекроются. Если `protocol` вошёл первым — `temp` подождёт ≈770 мс
  на мьютексе, что в одну итерацию своей петли.
- **Кэш в `temp_service`**: последнее валидное значение хранится в
  volatile-полях; одиночный writer (`task_temp` или `cmd_temp READ`) +
  атомарные `int16_t/uint32_t/bool` на Cortex-M4 → мьютекс на чтение
  кэша не нужен. Аггрегирующего стрима нет — каждый сенсор шлёт свой
  префикс (`$T18`, `$H`, `$P`, `$M`).
- **Drag-эффект на ISR**: внутри `ow_*` стоит `__disable_irq()` на время
  бит-слота (≤ 1 мс на reset, ~70 мкс на бит). Прерывания UART/TIM/SysTick
  поставлены в очередь NVIC и выполняются сразу после `__enable_irq()`.
  В одной транзакции это до ~1 мс «слепой зоны» — критичные ISR (motor
  step) лучше не сажать на тот же временной бюджет.

### Анализ стека

Грубая оценка кадров (newlib-nano, без `%f`):

| Кадр                          | Прибл. размер   |
|-------------------------------|-----------------|
| TCB save area / RTOS overhead | ~80 байт        |
| `task_temp` локальные         | ~60 байт (`tstr[8]`, `buf[48]`, `c10`, `n`) |
| `ds18b20_read_blocking`       | ~30 байт (`scratch[9]`, `c10`, `st`, `raw`) |
| `vsnprintf` newlib-nano       | ~300–400 байт   |
| `uart2_send` + LL HAL         | ~30 байт        |
| Запас на ISR-кадр (FreeRTOS port) | ~100 байт   |
| **Итого пик**                 | **≈ 600–700 байт** |

1024 — комфортный запас, но без перебора. Если когда-нибудь понадобится
поджать RAM — можно урезать до 768, но **не ниже** без `configCHECK_FOR_STACK_OVERFLOW`
проверки на реальном железе.

### Создание мьютекса и порядок init

`s_bus_mutex` создаётся внутри `ds18b20_init()` через `osMutexNew(NULL)`.
Это значит: **`ds18b20_init()` обязан быть вызван до `osKernelStart()` и
до создания `task_temp`**. Сейчас порядок такой:

```
app_init()
   └─ bsp_init()
       └─ ds18b20_init()           ← мьютекс создаётся здесь
app_run()
   └─ osKernelInitialize()
   └─ osThreadNew(task_temp, …)    ← поток создан, но ещё не бежит
   └─ osKernelStart()              ← планировщик стартует, task_temp идёт
```

Если переставить `ds18b20_init()` после `osKernelStart()` — `osMutexNew`
вернёт NULL (CMSIS-OS2 требует, чтобы мьютекс создавался при работающем
kernel'е, либо чтобы dynamic-allocation был доступен). Драйвер
страхуется проверкой `osKernelGetState() == osKernelRunning` перед
acquire/release — но если мьютекс не создан, защиты от гонки тоже нет.
Поэтому текущий порядок ломать нельзя.

## Поток данных

```
   PB12 (1-Wire)
      │
      ▼
  onewire driver  (bit-bang, DWT delay, irq-mask)
      │
      ▼
  ds18b20 driver  (Skip ROM → Convert T → Read Scratchpad → CRC8)
      │
      └─► ds18b20_read_blocking()
              ▲                  ▲
              │                  │
           task_temp         shell.c (TEMP READ)
              │                  │
              │                  └─► +OK TEMP <value> (синхронно)
              │
              ├─► temp_service_publish(c10) ─► temp_service кэш (volatile)
              │
              └─► uart2_send($T18, <ts>, <temp>)
```

## Алгоритм одного измерения

[`ds18b20_read_blocking()`](../firmware/src/devices/ds18b20/src/ds18b20.c#L37):

1. `ow_reset()` → ждём presence-pulse. Нет → `DS18B20_NO_DEVICE`.
2. `ow_write_byte(0xCC)` — **Skip ROM** (на шине единственное устройство).
3. `ow_write_byte(0x44)` — **Convert T**.
4. `osDelay(760 мс)` — `tCONV_max` для 12 бит = 750 мс, +10 мс запаса.
5. `ow_reset()` повторно.
6. `ow_write_byte(0xCC)` — Skip ROM.
7. `ow_write_byte(0xBE)` — **Read Scratchpad**, читаем 9 байт.
8. Если все 9 байт `0xFF` — обрыв/нет питания → `DS18B20_BAD_VALUE`.
9. Считаем CRC-8 Dallas (poly 0x31, reflected 0x8C) по первым 8 байтам и
   сравниваем со scratchpad[8]. Несовпадение → `DS18B20_BAD_CRC`.
10. `raw = scratch[0] | (scratch[1] << 8)` (signed).
    `c10 = raw * 10 / 16` — температура × 10 °C.
11. Clamp по datasheet: `[-550 .. +1250]` (× 10 °C ≡ −55.0 … +125.0 °C).

Конвертация по умолчанию **12-битная**: разрешение 1/16 °C ≈ 0.0625 °C,
время преобразования до 750 мс. Регистр конфигурации DS18B20 не
переписывается — пользуемся заводскими настройками.

## Формат температуры в API

- В прошивке всё значение хранится как `int16_t c10` — десятые градуса
  Цельсия (`266` ⇒ 26.6 °C, `-125` ⇒ −12.5 °C).
- На UART форматируется без `%f` (newlib-nano не тащит float-printf):
  [`temp_format_c10()`](../firmware/src/app/src/temp_service.c#L49) →
  `"<sign><int>.<frac>"`, например `"-12.5"`. Буфер ≥ 8 байт хватает на
  весь диапазон.

## CLI команды (USART2, shell)

Реализация — [`shell.c::cmd_temp`](../firmware/src/middleware/shell/src/shell.c).

| Команда             | Действие                                            | Ответ |
|---------------------|-----------------------------------------------------|-------|
| `TEMP READ`         | Синхронное разовое чтение, блок shell ≈770 мс       | `+OK TEMP <value>` / `-ERR TEMP no-device\|bad-crc\|bad-value` |
| `TEMP ON`           | Включить периодический поток `$T18`                 | `+OK TEMP ON` |
| `TEMP OFF`          | Выключить поток                                     | `+OK TEMP OFF` |
| `TEMP RATE <hz>`    | Задать частоту (для DS18B20 практически только 1 Hz)| `+OK TEMP RATE <hz>` / `-ERR TEMP bad-rate min=1 max=1` |
| `TEMP CONFIG`       | Прошить EEPROM датчика в 12-бит (см. ниже). Если уже 12-бит — EEPROM не пишется. | `+OK TEMP CONFIG 12bit` / `-ERR TEMP no-device\|bad-crc\|verify-failed` |

Частота по умолчанию — **1 Гц** (period 1000 мс). Минимум период — 800 мс
(`tCONV_max` 750 мс + запас на reset/scratchpad), что даёт максимум 1 Hz при
целочисленной арифметике. Если потребуется ниже 1 Hz — добавлять отдельную
команду либо парсер дробных значений. Константы — `TEMP_RATE_*` /
`TEMP_PERIOD_*` в [`temp_service.h`](../firmware/src/app/inc/temp_service.h).

## Коды ошибок драйвера

| Код                     | Когда                                            | Поведение `task_temp` |
|-------------------------|--------------------------------------------------|-----------------------|
| `DS18B20_OK`            | Чтение и CRC ОК                                  | Публикация + `$T18`  |
| `DS18B20_NO_DEVICE`     | Нет presence-pulse — обрыв/не подключён          | `temp_service_invalidate()`, **молчим** (без `!FAULT` чтобы не спамить раз в секунду) |
| `DS18B20_BAD_CRC`       | CRC8 scratchpad не сошёлся                       | Тоже invalidate, молча |
| `DS18B20_BAD_VALUE`     | Все 9 байт `0xFF` (питание/проводка/глюк)        | Тоже invalidate, молча |

Хост видит «нет `$T18`» и сам делает выводы — этого достаточно для UI.

## Известные ограничения

- **Только Skip ROM**, поиск ROM не реализован → допускается **ровно одно
  устройство** на шине.
- На время каждой операции прерывания глобально замаскированы. Длинная
  операция — `ow_reset()` ≈ 1 мс. ISR с жёстким требованием к latency
  должны это учитывать.
- Из-за `osDelay(760 мс)` чтение **блокирует** вызывающую задачу почти
  на секунду — поэтому опрос вынесен в отдельный поток `temp` с обычным
  приоритетом, а `TEMP READ` через shell тоже допустимо блокирует только
  shell.
- Параметры разрешения (R0/R1 в configuration register) автоматически на
  ребуте **не** меняются. Конфиг хранится в EEPROM датчика и переживает
  power cycle, поэтому если чип ранее использовался в другом проекте с
  9/10/11-бит — он останется в этом режиме до явной прошивки. Прошить в
  12-бит руками — `TEMP CONFIG` (см. ниже «Прошивка разрешения»).

## Прошивка разрешения

DS18B20 имеет в scratchpad'е байт `CONFIG` (R1:R0 + read-as-1 биты), который
определяет разрядность преобразования. Заводское значение — 12 бит, но это
**EEPROM-ная** настройка: любая запись через `Write Scratchpad (0x4E)` +
`Copy Scratchpad (0x48)` сохраняется в нелетучей памяти датчика и переживает
power cycle. Поэтому чип, который где-то раньше прошили в 9-бит, после
перепайки на эту плату **продолжит работать в 9-бит** — данные приходят, но
шаг 0.5 °C, и при медленном нагреве кажется, что сенсор «застрял».

Симптом распознаётся по приращению `raw` (нижние 16 бит scratchpad[0..1]):

| Битность | `raw` step | Видимый шаг °C |
|----------|-----------|----------------|
| 9        | 8         | 0.5            |
| 10       | 4         | 0.25           |
| 11       | 2         | 0.125          |
| 12       | 1         | 0.0625         |

Команда [`TEMP CONFIG`](../firmware/src/middleware/shell/src/shell.c) →
[`ds18b20_configure_resolution(DS18B20_RES_12BIT)`](../firmware/src/devices/ds18b20/src/ds18b20.c)
делает следующее:

1. Read Scratchpad → проверяем CRC, читаем текущий `CONFIG`.
2. Если уже совпадает с целью — **EEPROM не трогается** (экономим ресурс).
3. Иначе Write Scratchpad: `TH=0x7F` (+127 °C), `TL=0x80` (−128 °C),
   `CONFIG=0x7F` (12-бит). TH/TL ставим за пределы реального диапазона
   датчика, чтобы alarm-search никогда не срабатывал — мы им не пользуемся.
4. Copy Scratchpad → `osDelay(15 мс)` (`tWR_max = 10 мс` + запас).
5. Перечитать scratchpad, сверить CRC и `scratch[4] == 0x7F`. Если не сошлось
   — `-ERR TEMP verify-failed`.

Запись в EEPROM датчика имеет ресурс ≥50000 циклов по datasheet'у. Этого
с большим запасом хватает на любой сценарий, но автоматически на каждом
ребуте мы не прошиваем — оператор делает это один раз руками после монтажа
нового сенсора. Если нужно вернуть в 9/10/11 бит — добавлять параметр в CLI
(сейчас команда хардкодит 12-бит).

### Что меняется после `TEMP CONFIG`

- `tCONV` становится 750 мс (для 9-бит было ~94 мс) — но `task_temp` всё равно
  ждёт 760 мс независимо от разрешения, так что цикл не ускорится при
  понижении разрядности и не сломается при повышении.
- Шаг температуры — 0.0625 °C (раньше при 9-бит было 0.5 °C). На UART
  приходит десятая, поэтому видимый шаг — 0.1 °C.
- CRC и формат scratchpad'а не меняются.
