# DS18B20 — датчик температуры

Сводка по прошивочной интеграции DS18B20: что подключено, как опрашивается,
какие команды CLI, какие коды ошибок и в каком потоке всё выполняется.

## Аппаратное подключение

| Сигнал   | Пин        | Режим                         |
|----------|------------|-------------------------------|
| DQ       | **PB12**   | GPIO output, **open-drain**, speed HIGH, internal pull-up как страховка |
| VDD      | 3.3 В      | внешний резистор **4.7 кΩ от DQ к 3.3 В обязателен** |
| GND      | GND        |                               |

Источник правды по выводу — [`PIN_DS18B20_*`](../firmware/src/bsp/inc/bsp_pins.h#L26-L27)
в `bsp_pins.h`. Внутренний WPU не вытягивает шину достаточно быстро на
длинных проводах, поэтому внешний 4.7к — обязательный, не «желательный».

## Шина и тайминги

Используется **1-Wire master, программный bit-bang на GPIO** (Maxim AN-126,
Standard speed). Микросекундные задержки реализованы через `DWT->CYCCNT`
(счётчик тактов ядра), `s_cyc_per_us = SystemCoreClock / 1 000 000`.
Драйвер: [`firmware/src/drivers/onewire/`](../firmware/src/drivers/onewire/).

| Слот / операция            | Код       | Длительность |
|----------------------------|-----------|--------------|
| reset low                  | `OW_T_H`  | 480 мкс      |
| reset wait → presence sample | `OW_T_I` | 70 мкс      |
| reset recovery             | `OW_T_J`  | 410 мкс      |
| write-1 low / read init    | `OW_T_A`  | 6 мкс        |
| write-1 tail               | `OW_T_B`  | 64 мкс       |
| write-0 low                | `OW_T_C`  | 60 мкс       |
| write-0 recovery           | `OW_T_D`  | 10 мкс       |
| read sample delay          | `OW_T_E`  | 9 мкс        |
| read tail                  | `OW_T_F`  | 55 мкс       |

Бит-слот ≈ 70 мкс, байт ≈ 0.6 мс, reset ≈ 1 мс. **Все транзакции выполняются
с глобально замаскированными прерываниями** (`__disable_irq()` на время
слота), иначе ISR съедет тайминг и устройство не увидит правильный slot.
Это потолок latency других ISR на время операции — стоит держать в уме.

## АЦП и DMA — почему их нет

DS18B20 **не использует АЦП и не использует DMA**. Это цифровой датчик с
интерфейсом 1-Wire поверх одного GPIO; вся «оцифровка» происходит внутри
самого чипа, MCU только обменивается байтами по протоколу. DMA для
GPIO-bit-bang со строгими микросекундными слотами не применим в принципе —
управление линиями идёт инструкциями ядра под `__disable_irq()`.

В прошивке в целом:
- АЦП не инициализирован, периферия `ADCx` не используется (ток мотора в
  [`task_telemetry.c`](../firmware/src/app/src/tasks/task_telemetry.c) пока
  захардкожен в 0 — там стоит `TODO: ADC ток`).
- DMA сейчас задействован только в драйвере UART
  ([`firmware/src/drivers/uart/`](../firmware/src/drivers/uart/)).

## Размещение по задачам FreeRTOS

Создание потоков — в [`app_main.c`](../firmware/src/app/src/app_main.c).

| Задача         | Стек | Приоритет          | Что делает с DS18B20 |
|----------------|------|--------------------|----------------------|
| `temp`         | 1024 | `osPriorityNormal` | **Выделенный поток под датчик.** Периодический опрос (`Convert T → 760 мс → Read Scratchpad`), публикация в `temp_service` и эмиссия `$T18,...` в UART |
| `diag`         |  256 | `osPriorityNormal` | LED-маяк 1 Гц. С DS18B20 не работает — оставлен только как «жив ли планировщик» |
| `protocol`     | 1024 | `osPriorityNormal` | Через CLI выполняет синхронное `TEMP READ` (блокирует shell ≈770 мс) |
| `telem`        | 1024 | `osPriorityNormal` | Подмешивает последнее значение из `temp_service` в основной стрим `$T,<ts>,<pos>,<cur>,<temp>` |

Шина — одна, доступ из `temp` и `protocol` сериализуется **мьютексом**
`s_bus_mutex` внутри `ds18b20_read_blocking()`
([`ds18b20.c:14`](../firmware/src/devices/ds18b20/src/ds18b20.c#L14)).
До старта планировщика мьютекс не работает — драйвер это явно проверяет
через `osKernelGetState()`.

## Поток данных

```
   PB12 (1-Wire)
      │
      ▼
  onewire driver  (bit-bang, DWT delay, irq-mask)
      │
      ▼
  ds18b20 driver  (Skip ROM → Convert T → Read Scratchpad → CRC8)
      │
      ├──► ds18b20_read_blocking()
      │         ▲                  ▲
      │         │                  │
      │      task_temp         shell.c (TEMP READ)
      │         │
      │         ▼
      │   temp_service_publish(c10)
      │         │
      │         ▼
      │   ┌─────────────┐
      │   │ temp_service│  (последнее валидное значение + ts, volatile)
      │   └─────────────┘
      │         │
      │         ▼
      │   task_telemetry  →  $T,<ts>,<pos>,<cur>,<temp>
      │
      └──► task_temp  →  $T18,<ts>,<temp>   (отдельный поток температуры)
```

## Алгоритм одного измерения

[`ds18b20_read_blocking()`](../firmware/src/devices/ds18b20/src/ds18b20.c#L37):

1. `ow_reset()` → ждём presence-pulse. Нет → `DS18B20_NO_DEVICE`.
2. `ow_write_byte(0xCC)` — **Skip ROM** (на шине единственное устройство).
3. `ow_write_byte(0x44)` — **Convert T**.
4. `osDelay(760 мс)` — `tCONV_max` для 12 бит = 750 мс, +10 мс запаса.
5. `ow_reset()` повторно.
6. `ow_write_byte(0xCC)` — Skip ROM.
7. `ow_write_byte(0xBE)` — **Read Scratchpad**, читаем 9 байт.
8. Если все 9 байт `0xFF` — обрыв/нет питания → `DS18B20_BAD_VALUE`.
9. Считаем CRC-8 Dallas (poly 0x31, reflected 0x8C) по первым 8 байтам и
   сравниваем со scratchpad[8]. Несовпадение → `DS18B20_BAD_CRC`.
10. `raw = scratch[0] | (scratch[1] << 8)` (signed).
    `c10 = raw * 10 / 16` — температура × 10 °C.
11. Clamp по datasheet: `[-550 .. +1250]` (× 10 °C ≡ −55.0 … +125.0 °C).

Конвертация по умолчанию **12-битная**: разрешение 1/16 °C ≈ 0.0625 °C,
время преобразования до 750 мс. Регистр конфигурации DS18B20 не
переписывается — пользуемся заводскими настройками.

## Формат температуры в API

- В прошивке всё значение хранится как `int16_t c10` — десятые градуса
  Цельсия (`266` ⇒ 26.6 °C, `-125` ⇒ −12.5 °C).
- На UART форматируется без `%f` (newlib-nano не тащит float-printf):
  [`temp_format_c10()`](../firmware/src/app/src/temp_service.c#L49) →
  `"<sign><int>.<frac>"`, например `"-12.5"`. Буфер ≥ 8 байт хватает на
  весь диапазон.

## CLI команды (USART2, shell)

Реализация — [`shell.c::cmd_temp`](../firmware/src/middleware/shell/src/shell.c#L174).

| Команда             | Действие                                            | Ответ |
|---------------------|-----------------------------------------------------|-------|
| `TEMP READ`         | Синхронное разовое чтение, блок shell ≈770 мс       | `+OK TEMP <value>` / `-ERR TEMP no-device|bad-crc|bad-value` |
| `TEMP START`        | Включить периодический поток `$T18`                 | `+OK TEMP START` |
| `TEMP STOP`         | Выключить поток                                     | `+OK TEMP STOP`  |
| `TEMP PERIOD <ms>`  | Задать период (`800 ≤ ms ≤ 60000`)                  | `+OK TEMP PERIOD <ms>` / `-ERR TEMP bad-period min=800 max=60000` |

Период по умолчанию — **1000 мс**, минимальный — **800 мс** (`tCONV_max` 750 мс
+ запас на reset/scratchpad). Константы — `TEMP_PERIOD_*` в
[`temp_service.h`](../firmware/src/app/inc/temp_service.h#L13-L15).

## Стримы телеметрии

| Стрим                                  | Источник         | Когда отправляется |
|----------------------------------------|------------------|--------------------|
| `$T18, <ts_ms>, <temp>\r\n`            | `task_temp`      | После каждого успешного чтения, если `TEMP START` |
| `$T, <ts_ms>, <pos>, <cur>, <temp>\r\n`| `task_telemetry` | Если `TELEM ON`; температура — последнее валидное из `temp_service` (или 0.0, если ещё не прочитана) |

## Коды ошибок драйвера

| Код                     | Когда                                            | Поведение `diag` |
|-------------------------|--------------------------------------------------|------------------|
| `DS18B20_OK`            | Чтение и CRC ОК                                  | Публикация + `$T18`  |
| `DS18B20_NO_DEVICE`     | Нет presence-pulse — обрыв/не подключён          | `temp_service_invalidate()`, **молчим** (без `!FAULT` чтобы не спамить раз в секунду) |
| `DS18B20_BAD_CRC`       | CRC8 scratchpad не сошёлся                       | Тоже invalidate, молча |
| `DS18B20_BAD_VALUE`     | Все 9 байт `0xFF` (питание/проводка/глюк)        | Тоже invalidate, молча |

Хост видит «нет `$T18`» и сам делает выводы — этого достаточно для UI.

## Известные ограничения

- **Только Skip ROM**, поиск ROM не реализован → допускается **ровно одно
  устройство** на шине.
- На время каждой операции прерывания глобально замаскированы. Длинная
  операция — `ow_reset()` ≈ 1 мс. ISR с жёстким требованием к latency
  должны это учитывать.
- Из-за `osDelay(760 мс)` чтение **блокирует** вызывающую задачу почти
  на секунду — поэтому опрос вынесен в отдельный поток `temp` с обычным
  приоритетом, а `TEMP READ` через shell тоже допустимо блокирует только
  shell.
- Параметры разрешения (R0/R1 в configuration register) не меняются —
  всегда 12 бит.
